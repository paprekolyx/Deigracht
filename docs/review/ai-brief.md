# AI-бриф для внешнего независимого ревьюера

**Ведёт:** аналитик проекта · Albert23NO@ya.ru
**Статус:** редакция 1.0 · 07.10.2026 · создан волной v0.3.1 по записке
приёмки З3… З4. Документ [С]: обновляется перед каждым раундом независимого
ревью (регламент §6.3). **Раунд 1 — после волны v0.4.0.**
**Назначение:** внешний ревьюер (ИИ-ассистент без контекста переписки)
получает этот файл первым и за один проход понимает контекст, ограничения
и формат отчёта.

---

## 1. Проект в одном абзаце

**Дейгрихт (Deigracht)** — бесплатный некоммерческий статический веб-редактор
для оформления хоумбрю-документов к D&D и другим НРИ: пользователь пишет
Markdown с блоками Homebrewery V3 слева — справа видит книжный разворот
(пергамент, колонки, капители, статблоки), печатает в PDF (A4/Letter).
Клиентский проект **без сервера, базы, аккаунтов и шаринга** (решения
владельца ВЛ-04/ЮР-01/ЮР-02): документы живут в localStorage браузера,
передаются файлами (.md, самодостаточный .html, PDF). Стек: HTML5/CSS3/
vanilla JS без сборки и без внешних CDN (ADR-001); собственный парсер
Markdown+V3 (AST → программный DOM, без innerHTML); пагинация — страницы
фиксированной геометрии с JS-измерением переполнения колонок; шрифты —
4 семейства OFL с кириллицей, локально (ADR-002); хостинг — GitHub Pages
с `.nojekyll` (Jekyll/Liquid конфликтует с синтаксисом `{{…}}` — грабля №14).
Эталон приёмки — синтетическая структурная копия документа владельца
(`data/etalon/etalon-sint.md`, 178 632 знака, frozen-метрики в metrika.md):
авторский текст в репозитории не публикуется (грабля №12).

## 2. Жёсткие ограничения (предложения вне их — не принимаются)

1. **Нет сервера и бэкенда** в любом виде (ВЛ-04): ни аккаунтов, ни базы,
   ни шаринга, ни проксирования; «перенести рендер на сервер», «добавить
   API» — отклоняется без обсуждения (исключение-гейт: ВЛ-12, открыт,
   default — отрицательный).
2. **Нет сборщиков, фреймворков, npm-зависимостей и внешних CDN** (ADR-001):
   «перепиши на React/Vite/TS», «подключи marked.js» — отклоняется;
   сайт обязан открываться двойным кликом по index.html (file://).
3. **Изображения не реализуются до v1.0.0** (решение владельца 07.10.2026):
   черновик — только текст и таблицы; находки «картинки не работают» —
   не баги, а граница (fp №18).
4. **Кириллица обязательна** во всём: шрифты только с полной кириллицей
   (OFL 1.1); интерфейс только на русском (i18n — не раньше v1.x, ВЛ-09).
5. **Юридический контур:** Fan Content Policy WotC (бесплатно, без
   монетизации, без копирования оформления официальных книг); SRD 5.1 —
   только с атрибуцией CC-BY-4.0; ничего из ассетов WotC/Homebrewery
   (код Homebrewery не копируется — MIT-оригинал лишь образец синтаксиса).
6. **Дисциплина проекта:** SemVer-волны, документооборот и трекерные коды —
   по `docs/reglament.md`; ревьюер не предлагает править исторические
   документы ([Н]/[З]) и не предлагает изменить порядок волн без ссылки
   на решение владельца.
7. **Производительность и безопасность как границы:** CSP `default-src
   'self'` (+ style 'unsafe-inline' для @page-инъекции); XSS-модель —
   «парсер не создаёт исполняемых узлов»; квота localStorage ~5 МБ —
   честное предупреждение, а не silent fail.

## 3. Что читать и в каком порядке (файлы репозитория)

1. `docs/reglament.md` — правила проекта (волны, циклы документов, грабли);
2. `docs/reestr.md` — реестр документации: что зачем и когда меняется;
3. `docs/plan/plan-razrabotki.md` — волны, DoD, оценки, трекер АН;
4. `docs/plan/otchet.md` — анализ источников, **ADR-001…004**, матрица
   совместимости V3 (§1.4, включая осознанные расхождения), риски R1–R8,
   проверка названия (§7);
5. `docs/tehpasport.md` — фактические архитектура, модули, ограничения (§10),
   эксплуатационные заметки (§9);
6. `SECURITY.md` — честные границы защиты (что есть и чего сознательно нет);
7. `LICENSE.md` — трёхчастная лицензия и оговорки;
8. `docs/feature-proposals.md` — fp-карты: реализовано / бэклог / отменено;
9. `docs/plan/voprosy-vladeltsu.md` — решения владельца (ВЛ/ЮР) с датами;
10. `data/etalon/metrika.md` + `data/etalon/etalon-sint.md` — frozen-метрики
    регресс-эталона;
11. `docs/update/update-v0XX.md` — инструкции волн (состав и чек-листы);
    `docs/priemka/*` — записки приёмки и маршруты;
12. Код (порядок загрузки в браузере = порядок чтения): `assets/js/`
    config → util → parser → blocks → render → pages → storage → pdf →
    snippets → export → editor → help; стили `assets/css/` fonts → tokens →
    editor → theme-book → print;
13. Тесты: `tests/check-repo.py` (12 групп целостности), `tests/parser-smoke.js`
    (89 проверок: safeUrl-вектора, AST, блоки V3, fuzz-30, frozen-метрики).

## 4. Область проверки раунда 1 (после v0.4.0)

- **Парсер:** корректность Markdown+V3 на эталоне и fuzz-входах; XSS-инертность
  (safeUrl, отсутствие innerHTML, экранирование); обработка рваного ввода;
- **Пагинация:** переполнения/дробление (таблицы с повтором шапки, абзацы,
  списки), директива column-count, стабильность нумерации при правках;
- **Печать:** A4/Letter 1:1 без пустых и обрезанных страниц, блоки не «едут»,
  модалка печати блокирует фоновый скролл;
- **Безопасность:** CSP фактически = заявленному (SECURITY §2); данные не
  покидают браузер; секреты отсутствуют;
- **Производительность:** эталон 178 632 знака — рендер/пагинация в пределах
  DoD (debounce 300 мс, полный перерендер ≤2 с);
- **Целостность документации:** реестр ↔ фактический состав; версии в точках
  синхронизации; истории ревизий; соблюдение регламента (включая §3.5 —
  отсутствие ссылок на сторонние проекты вне otchet.md);
- **Читаемость кода владельцем** (владелец = аналитик = единственный
  разработчик): простота > cleverness; комментарии — зачем, а не что.

## 5. Формат отчёта ревьюера

- Файл: `docs/review/review-v040.md` (имя — по волне раунда);
- находки: **Ф-01, Ф-02…** — каждая: суть, серьёзность (критическая/
  средняя/низкая), воспроизведение (шаги или входные данные), место
  (файл:строка), предложение в рамках ограничений §2;
- текст ревьюера **[З] замораживается** после публикации: правки — только
  служебные вставки аналитика (журнал решений §4.2, статусы находок);
- трекер статусов находок — **один** документ (раунд = один файл,
  грабля №5); расхождения верификации — В-xx/Н-xx внутри того же файла;
- если предложение противоречит ADR/регламенту/решению владельца —
  оформлять как «наблюдение с указанием противоречия», не как находку.

## 6. Чего ревьюеру делать не нужно

- не предлагать сервер, сборку, фреймворки, CDN, i18n, изображения до v1.0.0
  (ограничения §2 — решения владельца, а не долги);
- не тестировать визуальную стилистику «на вкус» против официальных книг
  WotC (сравнение запрещено лицензионно, ВЛ-11);
- не править документы и код напрямую — только отчёт по §5.
