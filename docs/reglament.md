# Регламент ведения проекта Deigracht

**Версия документа:** 1.2 · 07.10.2026
**Статус:** основные правила ведения проекта; создан волной v0.0.1.
Регламент — событийный документ [С]: правится при появлении нового правила
(новая ревизия + строка истории в конце). Правила, вынесенные из практики
предыдущих проектов, помечены «(урок практики …)». Ссылки на сторонние
проекты в публикуемых документах не используются — анализ допустим только
в `docs/plan/otchet.md` (решение владельца 07.10.2026, грабля №8).

---

## 0. Управление проектом

0.1. **Ведущий аналитик = владелец проекта** (решение 07.10.2026):
отдельного согласования не требуется — решение владельца, зафиксированное
в документе с датой и кодом (ВЛ/АН), является достаточным основанием
для исполнения.
0.2. Решения фиксируются в соответствующих документах: продуктовые —
в `docs/plan/voprosy-vladeltsu.md`, архитектурные — ADR в
`docs/plan/otchet.md`, операционные — в трекере АН
(`docs/plan/plan-razrabotki.md` §6).

## 1. Волны и версионирование

1.1. **Волна ≈ один MINOR версии** (SemVer): MAJOR — несовместимая
архитектура, MINOR — волна функциональности, PATCH — правки и хотфиксы
внутри волны.
1.2. Особые диапазоны: **0.0.x — подготовка проекта** (документальные волны,
кода сайта нет); **0.x — черновик** (сайт-макет на GitHub Pages);
**1.0.0 — стабильный релиз** (статический сайт; серверная часть
не планируется — решение ВЛ-04 от 07.10.2026).
1.3. У каждой волны до старта зафиксированы: **состав работ, DoD (критерии
готовности), оценка в рабочих днях (РД)** — в `docs/plan/plan-razrabotki.md`.
Оценки РД после утверждения волны не пересматриваются (урок практики:
пересмотр оценок размывает план — правило F15 предыдущего проекта).
1.4. **Точки синхронизации версии** (сверяются check-repo с v0.1.0):
шапки `README.md`, `LICENSE.md`, `SECURITY.md` — строка
«Версия документа: 0.X.Y-draft · ДАТА»; с v0.1.0 — `SITE_VERSION` в
`assets/js/config.js` и версия на всех страницах сайта.
1.5. Таблица версий в README ведётся **строго в хронологическом порядке**
(урок практики: строка хотфикса, вставленная не на своё место, ломает
чтение истории).
1.6. Волна завершена, когда: код/документы загружены, DoD выполнен,
update-инструкция волны опубликована, check-repo даёт exit 0 (с v0.1.0),
версии в точках синхронизации подняты.
1.7. **Приёмка не переоткрывает волну** (установленное правило): замечания
приёмки уходят в следующую волну или в fp-карты.

## 2. Структура репозитория и циклы документов

2.1. Структура `docs/`:

```
docs/            reglament.md · reestr.md · tehpasport.md · feature-proposals.md
docs/plan/       plan-razrabotki.md · otchet.md · voprosy-vladeltsu.md
docs/update/     update-vXXXX.md — по файлу на волну [Н]
docs/priemka/    priemka-v0XX.md — обработка записок приёмки [С]
docs/review/     review-*.md — раунды ревью [З + служебные вставки]
docs/setup/      setup-*.md — инструкции подключения/публикации [С]
tests/           check-repo.py (с v0.1.0) [С]
```

2.2. **Циклы обновления документов** (обозначения реестра):
- **[В]** — меняется в каждой волне (версионно-синхронный);
- **[Н]** — создаётся заново в каждой волне, старые не редактируются;
- **[С]** — событийный: меняется при наступлении события;
- **[З]** — замороженный/исторический: текст неизменяем, допустимы только
  помеченные служебные вставки.

2.3. Истина о составе и циклах документации — в `docs/reestr.md`; файл
реестра имеет **постоянное имя, редакция — внутри, в шапке**; обновляется
перезаписью в составе пакета волны (урок практики: версионные имена файлов
плодят дубли).

## 3. Правила документов

3.1. Шапка каждого живого документа: название, **«Версия документа» /
«Дата»**, статус, ведущий (аналитик + контакт).
3.2. **История ревизий — в конце документа**, строкой на ревизию
(урок практики Д1: записи ревизий в шапке раздувают её и мешают чтению).
3.3. **Запрет дублирования при загрузке**: перед публикацией пакета каждый
MD-файл проверяется — `grep -c '^# '` = 1, число `##`-секций совпадает
с оглавлением (урок практики: документ был загружен двойным копированием
из-за fuzzy-замены блока со спецсимволами).
3.4. **Честность документации**: упрощения и границы черновика перечислены
явно (README, SECURITY §3); SECURITY.md описывает фактическое состояние,
а не намерения (урок практики v0.14.0 предыдущего проекта — здесь и далее
версии прошлого проекта не цитируются, правило общее).
3.5. Документы не ссылаются на неопубликованные рабочие материалы и на
сторонние проекты (исключение — `docs/plan/otchet.md`, анализ источников);
рабочие черновики аналитика — вне репозитория (каталог `drafts/`, .gitignore).
3.6. Даты — в формате ДД.ММ.ГГГГ; каждое решение владельца фиксируется
датой и источником (чат/почта) в соответствующем документе.

## 4. Ветки и коммиты

4.1. Единственная рабочая ветка — **main**; force-push не используется;
публикация сайта — Deploy from a branch (main /root).
4.2. Сообщение коммита — одно из двух:
- **версия пакета**: `0.0.2-draft` (загрузка состава волны);
- **ссылка на задачу/правило**: `(АН-03 п.2, регламент §4)` — точечные
  правки между волнами.
4.3. Волна загружается пакетом: 1–3 коммита на волну; состав пакета —
в §2 update-инструкции волны.
4.4. Правки «горящих» файлов (файл, живущий на GitHub в редактируемом
состоянии — например, config.js с SITE_VERSION) — только точечно,
веб-редактором, файл целиком не перезаписывается.

## 5. Трекерные коды

| Код | Значение | Где живёт |
|---|---|---|
| **АН-xx** | задача аналитика | трекер — `docs/plan/plan-razrabotki.md` §6 |
| **ВЛ-xx** | вопрос владельцу | `docs/plan/voprosy-vladeltsu.md` |
| **ЮР-xx** | юридический вопрос | там же, блок «Юрблок» |
| **fp №x** | карта функционала | `docs/feature-proposals.md` (номер сохраняется исторически, даже когда карта реализована или отменена — на него ссылаются документы; урок практики) |
| **Ф-xx** | находка ревью | `docs/review/review-*.md` |
| **В-xx / Н-xx** | расхождение / новая находка верификации волны | `docs/review/` |
| **З-xx / М-xx** | записка приёмки (крупная / мелкая) | `docs/priemka/priemka-v0XX.md` |
| **ADR-xxx** | архитектурное решение | `docs/plan/otchet.md`, раздел ADR |

Реализованная fp-карта переносится в блок «Уже реализовано» с указанием
версии — сразу после волны, до приёмки; отменённая — заменяется статусной
заглушкой с сохранением номера и кода решения.

## 6. Приёмка и ревью

6.1. **Приёмка**: после волны владелец присылает записки; аналитик создаёт
`docs/priemka/priemka-v0XX.md` (имя — по версии волны, актуальной на момент
обработки; документ создаётся не при каждой волне, а только при появлении
записок — установленное правило). Структура: крупные пункты (маршрут:
вопрос → план → fp/трекер) и мелкие правки (передаются в следующую волну
сводной таблицей); созданный файл не редактируется, кроме помеченных
служебных вставок и статусов.
6.2. **Ревью**: каждый раунд — отдельный документ `docs/review/review-vXXXX.md`
(установленное соглашение). Текст ревьюера **[З] заморожен**; аналитик
ведёт только журнал решений и статусы находок. Дубль-трекеры статусов не
создаются — истина по статусам раунда в одном документе (урок практики:
дублирующий файл статусов пришлось удалять).
6.3. Независимое ревью (внешний ИИ-ревьюер) — минимум раз в 3–4 кодовых
волны и обязательно перед v1.0.0.
6.4. Учитывая §0.1 (аналитик = владелец), записки приёмки могут
фиксироваться аналитиком со слов/сообщений владельца — с датой и пометкой
источника.

## 7. Инструкции обновлений

7.1. Каждая волна = новый файл `docs/update/update-vXXXX.md` **[Н]**;
созданные файлы больше не редактируются (старые пути и названия в них —
историческая запись).
7.2. Фиксированный состав разделов:
1. Что изменилось (в т.ч. «Задача волны»);
2. Файлы для загрузки в репозиторий (по папкам) — с постоянными
   напоминаниями этой волны;
3. Версия (точки синхронизации);
4. Публикация и проверка (чек-лист приёмки);
5. Финальная проверка;
6. Открытые пункты (не входят в волну);
7. Урок для регламента (если волна дала новую граблю).
7.3. **Документированное исключение (однократное):** `update-v001.md`
отредактирован в волну v0.0.2 по решению владельца от 07.10.2026 — удаление
ссылок на сторонний проект и историческая отметка о переименовании; состав
и факты волны v0.0.1 не изменялись. Впредь правило §7.1 действует
без исключений.

## 8. Тесты и качество

8.1. С волны v0.1.0 в репозитории живёт `tests/check-repo.py` —
автопроверка целостности без сети и БД (`python3 tests/check-repo.py`,
код выхода 0 = зелёный). **exit 0 — индикатор качества волны**; волна
не закрывается на красном check-repo.
8.2. Состав проверок растёт с волнами (минимум v0.1.0): REQUIRED-файлы;
версии в шапках README/SECURITY/LICENSE = SITE_VERSION; локальность всех
`src/href` (нет hotlink-скриптов); пары JS↔HTML; сбалансированность тегов;
отсутствие секретов-паттернов; отсутствие ссылок на сторонние проекты
вне otchet.md (грабля №8 — проверка `grep -ci` по списку имён); отсутствие
инородных символных включений (CJK-диапазоны и подобное — грабля №10).
Каждая новая грабля — новая проверка.
8.3. Ручной чек-лист приёмки каждой волны — §4 её update-инструкции.
8.4. Эталонный документ приёмки — «Всемирная история» владельца: с каждой
кодовой волны прогоняется на рендер и печать (регресс-эталон; второй
документ не требуется — блоки те же, ВЛ-10 от 07.10.2026).

## 9. Безопасность

9.1. Секреты не попадают в git никогда; `.gitignore` — с первого коммита;
в репозитории только `*.example`-конфиги.
9.2. SECURITY.md обновляется волной, которая сдвигает границы защиты;
расхождение SECURITY с фактом считается багом документации и чинится
вне очереди.
9.3. Персональные данные не собираются (ЮР-02); тестовые документы
создаются с вымышленными данными.

## 10. Регистр грабель (уроки, унаследованные и свои)

| № | Грабля | Мера / где зашито |
|---|---|---|
| 1 | Дублирование MD-файла при загрузке fuzzy-заменой со спецсимволами | проверка `grep -c '^# '` = 1 перед публикацией (§3.3, update §5) |
| 2 | Нарушение хронологии таблицы версий | §1.5 + check-repo (с v0.1.0, АН-01) |
| 3 | SECURITY разошёлся с фактическим состоянием | §3.4, §9.2 |
| 4 | Версионные имена файлов реестра плодят дубли | §2.3: постоянное имя, редакция внутри |
| 5 | Дубль-трекер статусов ревью | §6.2: один документ — одна истина |
| 6 | Устаревшие пути docs/ в живых документах после перестройки | аудит путей каждой волной (update §5); исторические документы не правятся |
| 7 | Кириллица проваливается в fallback-шрифт (документ владельца в Homebrewery: Times New Roman вместо книжного шрифта) | шрифты — только с кириллицей, OFL, локально (otchet ADR-002); проверка эталонным документом (§8.4) |
| 8 | Ссылки на сторонние проекты («контекстные ссылки») попадают в публикуемые документы | внешние упоминания — только в otchet.md; контроль `grep` по именам проектов в финальной проверке волны (§3.5, §8.2, update §5) — решение владельца 07.10.2026 |
| 9 | Публикация под временным именем создала затраты на переименование (репозиторий, URL Pages, упоминания в документах) | проверка названия до создания репозитория (поиск + GitHub, шаблон — otchet §7); переименование — по инструкции setup-repo-pages шаг 0 |
| 10 | Инородные символы-включения (иероглифы и подобные артефакты инструментов подготовки текста) попадали в русскоязычные документы | финальная проверка волны сканирует MD-файлы на символы вне кириллицы/латиницы/пунктуации (update §5); с v0.1.0 — проверка в check-repo (§8.2) |

Новые грабли добавляются из §7 update-инструкций волн.
